# تقرير مراجعة توافق الواجهات مع مختلف مقاسات الشاشات

التاريخ: 19 أكتوبر 2026

## النتيجة ونطاق المراجعة

المشروع يحتوي بالفعل على دعم للموبايل، لكنه يحتاج تعديلات محددة قبل اعتبار تجربة الهاند هيلد جاهزة. أهمها: مساحات اللمس، بعض شبكات البطاقات ذات العرض الأدنى الثابت، تناسق الخطوط، وطريقة التعامل مع الجداول الكبيرة.

هذه مراجعة ساكنة للكود: تعريفات المسارات، ملفات الصفحات والمكونات المشتركة، وقواعد CSS وأولوية تطبيقها. لم تُنفذ جلسة اختبار مرئي بالمتصفح أو على جهاز فعلي، ولم تُجرّب خطوات الأعمال ببيانات فعلية. لذلك «مؤكد» هنا يعني وجود السبب في الكود، وليس قياس الشكل النهائي على شاشة. توصيات الاستخدام منفصلة عن العيوب المؤكدة، ولا توجد شهادة نجاح لكل مقاس.

لم يتم تعديل كود التطبيق أو بياناته. أُضيف هذا التقرير فقط بناءً على طلب التقرير أولاً.

بناءً على طلب تغطية كل المقاسات: التصميم المقترح مرن حسب المساحة المتاحة، مع نقاط تحقق من عرض 280 إلى 1920 بكسل CSS، بالطول والعرض. هذه نقاط اختبار مقترحة وليست اختبارات تم تشغيلها. دقة الشاشة الفيزيائية لا تساوي بالضرورة العرض المتاح للمتصفح.

## الموجود بالفعل ويمكن البناء عليه

- تعريف viewport سليم في `frontend/index.html` ويسمح بالتكبير.
- قائمة تنقل جانبية للشاشات الصغيرة، وزر فتحها 44×44.
- حقول وأزرار مشتركة كثيرة لها حد أدنى للارتفاع 44px عند عرض 768px أو أقل.
- قواعد لالتفاف العناوين والأسماء الطويلة، وتقييد الحاويات، وتمرير الجداول داخل حاوياتها.
- ضبط عرض وارتفاع عدد من الحوارات بحسب الشاشة، واستخدام `dvh` في مواضع متعددة.
- بعض صفحات مراجعة المبيعات بها بالفعل بديل بطاقات على الشاشات الصغيرة؛ لا يلزم تحويل كل جداولها من الصفر.
- دعم RTL والعربية، وخطوط محلية، وقواعد للوضع الداكن.

| متوسطة | `ScaleDevicesPage.jsx:979` يبقي حقلي IP وPort في عمودين بنسبة 2:1 دون تفرع للمقاس. | مساحة إدخال ضيقة داخل الحوار على الشاشات الصغيرة. | عمود واحد عند ضيق الحوار، وعمودان عندما تتسع المساحة. |

| تحقق مطلوب | `SignaturePad.jsx` يجهز أبعاد canvas عند تغير `height` فقط، ولا يعيد حسابها عند تغير العرض. | احتمال عدم تطابق مساحة الرسم ودقتها بعد تدوير الجهاز أو تغيير مساحة الحاوية. | إعادة القياس مع حفظ التوقيع، والتحقق من إحداثيات الرسم على شاشات عالية الكثافة. |

مهم: وجود قيمة 10px أو 12px داخل صفحة لا يثبت وحده أن المستخدم يراها بهذا الحجم؛ قواعد الخطوط العامة قد تتغلب عليها. لذلك لا يصح تكبير جميع القيم الصغيرة آلياً دون فحص المقاسات المحسوبة بالمتصفح.

| إيصال الميزان `/scale/receipt` | جداول إدخال وتوقيعان عبر canvas. | اختبار الرسم بإصبع، مسح التوقيع وتدوير الجهاز، والجداول مع الكيبورد. |
| مسودات الميزان `/scale/drafts` | جدول أدنى عرضه 1200px مع تمرير داخلي. | يفضل بطاقات مختصرة للموبايل؛ قياس مساحة الأزرار وعدم الاعتماد على التمرير للوصول لكل إجراء. |
| تفاصيل مسودة الميزان `/scale/drafts/:draftId` | ملخص مستند ومكونات عرض مرتبطة بالميزان. | تحقق من الملخص والتفاصيل والإجراءات والطباعة في حالتي الفتح والإغلاق. |
| أجهزة الميزان `/scale/devices` | جدول MUI وحوار إعدادات؛ حقلا IP وPort ثابتان بعمودين. | جعل الحقول عموداً واحداً عند الضيق، وقياس أزرار MUI الصغيرة داخل الجدول والحوار. |
| عناصر الميزان `/scale/item-elements` | جدول وحوار MUI وأزرار `size="small"`. | قياس أبعاد اللمس الفعلية، وضبط الإجراءات والحوارات حسب المساحة. |
| تصاريح الميزان `/scale/entry-exit-permits` | صفحة اختيار نوع التصريح. | تحقق من البطاقات ومساحة الضغط والعناوين. |
| تصريح الدخول `/scale/entry-exit-permits/entry` | غلاف لنموذج تصريح مشترك. | تجربة النموذج كاملاً والكيبورد والتأكيد وعرض نسخة الطباعة. |
| تصريح الخروج `/scale/entry-exit-permits/exit` | نفس النموذج بسياق خروج. | تجربة الحقول المشروطة في وضع الخروج مستقلاً. |

مسارات التحويل مثل `/review` و`/transfer/internal` و`/quality/pre-export` و`/order-rules` ليست شاشات مستقلة؛ تؤدي لشاشات أو وجهات سبق ذكرها. الملفات التي لا ترتبط مباشرة بمسار، مثل أغلفة صفحات المبيعات القديمة، لا تُحسب كشاشات إضافية للمستخدم.

## التعديلات المقترحة ونطاق تأثيرها

1. **مساحات اللمس المشتركة:** تعديل أزرار الأيقونات والزر الخاص ببطاقة GRPO، ومراجعة أزرار MUI ومربعات الاختيار. أثرها على الصفحات التي تستخدم المكونات نفسها؛ قد تتطلب زيادة ارتفاع الصف أو التفاف صف الأزرار.
2. **الشبكات الضيقة:** إصلاح بطاقات أوامر البيع والتسليم، وحقول إعداد أجهزة الميزان، ثم فحص الشبكات المتداخلة في معالجات الإنشاء. أثرها في ترتيب العناصر وعدد الأعمدة.
3. **الخطوط:** بناء أحجام واضحة للنصوص المهمة والثانوية والعناوين، وحل التعارض مع القواعد العامة. لا يُنصح بتكبير كل النصوص بقانون واحد؛ ذلك قد يزيد قص النصوص أو طول الصفحة.
4. **الجداول التشغيلية:** اختيار عرض موبايل مختصر للصفحات الأكثر استخداماً، خصوصاً مسودات الميزان. الإبقاء على التفاصيل الكاملة في شاشة أو حوار مستقل وعلى الجدول في المساحات الواسعة. هذا تغيير في طريقة العرض ويحتاج اتفاقاً على المعلومات الأساسية.
5. **التوقيع والخطوات والكيبورد:** ضبط سلوك التوقيع عند تغير المساحة، والتحقق من رؤية الخطوة الحالية والإجراء الأساسي عند فتح لوحة المفاتيح.

لا تتطلب هذه المقترحات بحد ذاتها تغيير منطق الأعمال أو واجهات API. تعديل عرض الجداول إلى بطاقات يظل اقتراحاً للتنفيذ بعد مراجعتك للتقرير.

## مقاسات التصميم المقترحة

هذه أهداف داخلية للمشروع، وليست مقاسات تم اعتمادها على جهاز أو ادعاء مطابقة معيار خارجي:

| العنصر | الهدف المقترح |
|---|---|
| النص الأساسي وحقول الإدخال | 16px افتراضياً مع السماح بالتكبير |
| النص الثانوي | 14px للمعلومات المقروءة المتكررة |
| عناوين الأقسام | 18–22px حسب المساحة |
| عنوان الصفحة | 22–28px على الشاشات الصغيرة، مع تدرج مناسب للشاشات الأوسع |
| مساحة الزر اللمسية | 44×44px على الأقل، و48px للإجراءات الميدانية المتكررة |
| الأيقونة داخل الزر | 20–24px؛ مساحة الضغط أكبر من الرسم |
| المسافة بين إجراءات متجاورة | نحو 8px حيث تسمح المساحة |
| النماذج عند ضيق المساحة | عمود واحد دون عرض أدنى يتجاوز الحاوية |
| الجداول الواسعة | تمرير داخل الحاوية أو بطاقات مختصرة؛ لا تصغير للنص لحشر الأعمدة |

يراعى نوع الإدخال أيضاً عبر `pointer: coarse`، لأن جهازاً لمسياً عريض الشاشة قد يظل محتاجاً أزراراً كبيرة حتى خارج نقاط الموبايل.

## التحقق المطلوب قبل اعتماد التنفيذ

- عروض CSS: 280، 320، 360، 390، 412، 480، 600، 768، 820، 1024، 1280، 1440، 1920، مع التحقق بين نقاط التحول لا عندها فقط.
- اتجاهان بالطول والعرض، وارتفاعات قصيرة مثل 320 و480 و560px.
- العربية والإنجليزية، والوضعان الفاتح والداكن، وتكبير النص/الصفحة.
- بيانات فارغة، تحميل، أخطاء، سجلات كثيرة، وأسماء وأكواد طويلة.
- كل خطوة فعلية في المعالجات، لا صفحة البداية فقط؛ كل حوار وقائمة مفتوحة، والكيبورد ظاهر.
- قياس المقاسات المحسوبة للخطوط والأزرار، وعدم الاكتفاء بوجود media query.
- عدم وجود تمرير أفقي للصفحة؛ التمرير المقصود يظل داخل الجدول أو الخريطة.
- اختبار اللمس وقارئ الباركود المتاح في التشغيل دون تنفيذ ترحيل على بيانات فعلية أثناء فحص الشكل.
- فصل العرض على الشاشة عن إخراج الطباعة، واختبار الاثنين بعد التعديلات المشتركة.

يوجد سكربت `frontend/scripts/audit-responsive.mjs` يمكن البناء عليه، لكنه لا يكفي وحده للاعتماد: يضبط `mobile:false`، ويستبدل `:draftId` فقط دون `:docEntry`، ويستخدم بيانات تجريبية عامة، ولا يمر عبر جميع خطوات التشغيل. لم يتم تشغيله في هذه المراجعة. يجب تطوير تغطيته قبل الاستناد إلى نتائجه لإعلان نجاح كل الصفحات.

## ترتيب التنفيذ المقترح

الأولوية الأولى: أزرار اللمس وشبكات 360px وزر بطاقة GRPO. بعدها ضبط الخطوط وحقول الحوارات. ثم تحسين الجداول التشغيلية والتوقيع، مع صور قبل/بعد لكل صفحة متأثرة واختبار المقاسات واللغتين. القرار الحالي هو تقديم التقرير؛ لم يبدأ تنفيذ هذه التعديلات.
